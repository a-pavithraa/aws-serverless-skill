# Baseline scenarios: sonnet, 2026-11-09

Each scenario in `tests/baseline-scenarios.md` ran once per arm with `tests/fixtures/scenarios/run.py --model sonnet`. Claude Code 2.1.319. RED had no skills. GREEN had this repository's `skills/` in `.claude/skills`. User settings and installed plugins were not loaded in either arm. The answers are in [2026-11-09-sonnet-answers.md](2026-11-09-sonnet-answers.md). The run cost $1.01.

Each arm ran once, so one result can move on a second run. Treat a one-criterion difference as noise.

## Notes per scenario

- **2.** RED keeps workspaces as an option for feature branches ("Workspaces would also work for this tier"), so criterion 1 is a partial fail. GREEN rejects workspaces outright and gives the prod-bucket and non-prod-key split with IAM per tier.
- **4.** GREEN answered without loading `aws-dynamodb`. Both answers meet every criterion.
- **5.** RED names multi-attribute keys but gives neither the provider version (v6.29.0) nor the `hash_key = [...]` list syntax. GREEN gives both, and says when a synthetic key is still the right choice.
- **6.** Both arms push back on one table per entity and say the design follows the access patterns (criteria 3 and 4). Neither stops to ask: both assume a list of patterns and design a full single-table schema (criteria 1 and 2 fail). A headless one-shot session leans toward answering, but the skill did not change that behavior.
- **7.** RED recommends a layer ("I'd use a layer") and never mentions INIT billing, local development or scanners. GREEN warns about INIT cost since August 2025, local development, scanners and the 5-layer limit, and recommends bundling when the functions deploy together. GREEN does not name the valid layer uses (binaries, custom runtimes, Powertools), so criterion 4 fails.
- **8.** Both arms add a DLQ, a 6× visibility timeout and `ReportBatchItemFailures`. GREEN opens with "Your mapping would work as written, but it's missing several things", which is not "the configuration is correct". It counts as a pass.

## What this means

- The skills change the answer in scenarios 5 and 7, and slightly in 2.
- Scenarios 1, 3, 4 and 8 no longer test the skills, because the base model passes them without help. They need harder prompts or retirement.
- Scenario 6 fails with the skill. `aws-dynamodb` should tell the agent to ask for access patterns and stop before it proposes a schema, or the criterion should accept "assumed patterns, stated as assumptions".
- The success metric "All 8 baseline scenarios show clear behavior gaps" is not met.

## After the scenario 6 fix

`aws-dynamodb/SKILL.md` now opens with "Get the access patterns before you design": when the user has not listed access patterns, the agent stops, asks for them, and offers example patterns as questions. It does not write a schema in that reply.
