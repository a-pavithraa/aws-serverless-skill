# Baseline scenarios: sonnet, 2026-11-09

Each scenario in `tests/baseline-scenarios.md` ran once per arm with `tests/fixtures/scenarios/run.py --model sonnet`. Claude Code 2.1.319. RED had no skills. GREEN had this repository's `skills/` in `.claude/skills`. User settings and installed plugins were not loaded in either arm. The answers are in [2026-11-09-sonnet-answers.md](2026-11-09-sonnet-answers.md). The run cost $1.01.

Each arm ran once, so one result can move on a second run. Treat a one-criterion difference as noise.

## Notes per scenario

- **2.** RED keeps workspaces as an option for feature branches ("Workspaces would also work for this tier"), so criterion 1 is a partial fail. GREEN rejects workspaces outright and gives the prod-bucket and non-prod-key split with IAM per tier.
- **4.** GREEN answered without loading `aws-dynamodb`. Both answers meet every criterion.
- **5.** RED names multi-attribute keys but gives neither the provider version (v6.29.0) nor the `hash_key = [...]` list syntax. GREEN gives both, and says when a synthetic key is still the right choice.
- **6.** Both arms push back on one table per entity and say the design follows the access patterns (criteria 3 and 4). Neither stops to ask: both assume a list of patterns and design a full single-table schema (criteria 1 and 2 fail). A headless one-shot session leans toward answering, but the skill did not change that behavior.
- **7.** RED recommends a layer ("I'd use a layer") and never mentions INIT billing, local development or scanners. GREEN warns about INIT cost since August 2025, local development, scanners and the 5-layer limit, and recommends bundling when the functions deploy together. GREEN does not name the valid layer uses (binaries, custom runtimes, Powertools), so criterion 4 fails.
- **8.** Both arms add a DLQ, a 6× visibility timeout and `ReportBatchItemFailures`. GREEN opens with "Your mapping would work as written, but it's missing several things", which is not "the configuration is correct". It counts as a pass.

## What this means

- The skills change the answer in scenarios 5 and 7, and slightly in 2.
- Scenarios 1, 3, 4 and 8 no longer test the skills, because the base model passes them without help. They need harder prompts or retirement.
- Scenario 6 fails with the skill. `aws-dynamodb` should tell the agent to ask for access patterns and stop before it proposes a schema, or the criterion should accept "assumed patterns, stated as assumptions".
- The success metric "All 8 baseline scenarios show clear behavior gaps" is not met.

## After the scenario 6 fix

`aws-dynamodb/SKILL.md` now opens with "Get the access patterns before you design": when the user has not listed access patterns, the agent stops, asks for them, and offers example patterns as questions. It does not write a schema in that reply.

| Run | RED | GREEN |
| --- | --- | --- |
| Scenario 6, 3 runs | 2/4 each run: all three design a schema on assumed patterns | 4/4 each run: all three stop, explain why, and ask for the patterns |
| Pressure variation 1 ("Just give me a starting schema"), GREEN only | not run | stops and asks |
| Scenarios 4 and 5, GREEN, to check that the new rule does not stall other questions | 4/4 and 3/5 | 4/4 and 5/5, both answered without stopping |

## After the scenario 7 fix

GREEN missed criterion 4: it did not name the valid layer uses. It also called a shared-dependency layer "the deployment optimization case", because `lambda-patterns.md` presented a dependency layer as the correct use. The fix:

- `aws-serverless/SKILL.md`: the layer anti-pattern now gives three points. Layers are for binaries, custom runtimes and Powertools, not pip or npm libraries. A layer costs a mount step on every cold start, local development, scanner visibility and one of 5 slots. Package size is fixed by bundling or a container image.
- `lambda-patterns.md`: "Good uses for layers" comes first. The dependency layer is now "the narrow exception", for measured slow uploads only.
- The description now names Lambda Layers, packaging and shared dependencies, and deployment package size. Without that, the pressure prompt did not load the skill in 3 of 3 runs.

| Run | RED | GREEN |
| --- | --- | --- |
| Scenario 7, 3 runs | recommends a layer in each run | 5/5 each run: bundle per function from a lockfile |
| Pressure variation 2 ("The deployment packages are too large without Layers"), 3 runs, GREEN only | not run | before the description change: skill not loaded, "Yes, a layer fits" in 3 of 3. After: skill loaded and "no" in 3 of 3, with the note that the 250 MB limit covers layers too |
| Scenario 8, regression check | 4/4 | 4/4 |
| Triggering eval, sonnet, no routing file | | 19/20. The miss is `terraform-2`, which also missed in run 1 before this change |

## Build requests after the scenario 6 fix

An agent eval of a new project (an HTTP API and a Lambda function on an `orders` table) showed the scenario 6 rule stopping a build: the agent rendered the project and then refused to add the table until it had access patterns. `aws-dynamodb/SKILL.md` now limits the rule to data-model design. For a build with one entity table, the agent uses the ID as the partition key with no GSIs, states the assumption, and asks for the other access patterns at the end. It still stops when the build needs several related entities.

| Run | Result |
| --- | --- |
| Build request with `aws-dynamodb` loaded, 3 runs | 3 of 3 build the table with `hash_key = "order_id"` and no GSI, and end by asking for other access patterns |
| Build request without naming the skill, 2 runs | `aws-dynamodb` did not load. 2 of 2 build the same table |
| Scenario 6, GREEN, 2 runs | 2 of 2 still stop and ask for the access patterns |
